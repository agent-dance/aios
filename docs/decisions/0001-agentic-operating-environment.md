# ADR 0001：AIOS 以 Agentic Operating Environment 形式落地

- 状态：Accepted
- 日期：2026-07-25

## 背景

AIOS 的产品目标不是再造一个传统意义上的内核、驱动栈和硬件抽象层，而是把“操作系统”的核心职责重组到 AI 时代：把用户意图、Agent 执行、UI 展现、能力授权、产物沉淀和审计回放统一到一个可控环境中。

这里有两个容易失控的方向：

1. 走“自研 OS / 自研内核”路线，会把项目立即拖入驱动、兼容层、启动链、更新通道、设备支持和安全补丁体系，工程量与产品验证节奏完全失衡。
2. 走“网页应用 + 一堆 Agent 插件”的路线，又会退化成普通桌面应用，无法建立系统级权限模型、统一的 Agent 生命周期、可信确认界面与稳定的交互语义。

因此 MVP 需要一个中间形态：既不是浏览器里的 SaaS，也不是重写一套真正的宿主操作系统，而是运行在现有 macOS / Windows / Linux 之上的宿主级 AI 元操作环境。

## 决策

AIOS 的 MVP 采用以下形态：

1. 产品定位为运行在宿主操作系统之上的 Agentic Operating Environment（面向 Agent 的元操作环境）。
2. 桌面外壳采用 Tauri 宿主能力承载，系统核心采用 Rust 实现，交互层采用 Web UI。
3. 架构形式采用模块化单体，而不是从第一天拆成多服务。
4. 所有“像操作系统一样”的能力——Agent 安装、能力申请、任务编排、动态 UI、产物沉淀、权限确认、审计追踪——都在这个环境内形成闭环。
5. MVP 明确不自研内核、不自研驱动、不承担硬件兼容层职责，不以容器编排式微服务作为起点。

## 设计原则

该决策约束后续实现遵循以下原则：

- 宿主 OS 负责基础设备与原生安全边界，AIOS 负责 Agent 时代的人机协作与能力治理。
- 所有高价值复杂性集中在“意图到结果”的闭环，而不是底层平台替换。
- UI、能力模型、运行时、审计模型必须共设计，不能分别堆砌。
- 能单进程保持强一致的部分，不提前分布式化。

## 备选方案

### 方案 A：自研真正的操作系统或内核层发行版

把 AIOS 作为新的系统发行版，掌控启动、进程、文件系统、网络栈和窗口系统。

### 方案 B：纯 Web / Electron 风格应用层产品

把 AIOS 当作“Agent 工作台”，仅提供普通应用级功能，通过浏览器或桌面容器承载。

### 方案 C：MVP 先拆成多服务 / 本地控制平面

把安装、调度、UI、权限、存储、Agent Store 从一开始做成多个本地服务，通过 IPC 或 HTTP 协作。

## 为何排除

### 排除方案 A 的原因

- 与 MVP 核心假设不匹配。当前需要验证的是 Agent 能否替代“应用安装”的能力模型，而不是验证硬件兼容能力。
- 研发投入严重偏离产品风险。最大的未知项在权限治理、动态 UI、Agent 契约、可信确认与可恢复执行，不在内核实现。
- 交付周期不可控。任何驱动、升级、兼容性问题都会淹没产品验证节奏。

### 排除方案 B 的原因

- 无法自然承载“像 OS 一样”的能力治理。它容易退化为一个聚合 Agent 的前端壳。
- 对宿主资源访问、安装生命周期、可信确认和本地审计的约束力不足。
- 用户心智上会被理解成“另一个工作台应用”，而不是 Agent 时代的操作环境。

### 排除方案 C 的原因

- 在问题尚未稳定前，服务拆分会制造更多接口和一致性成本。
- 本地微服务并不能天然提升安全，反而会提前引入鉴权、回放、编排和运维复杂度。
- 当前最重要的是先把单一可信边界做实，再决定哪些边界需要独立进程或远程化。

## 后果

### 正面后果

- MVP 可以把工程重点压在真正有产品辨识度的层面：Agent 安装、动态 UI、Capability Broker、Mission / Run / Artifact、可信确认与审计。
- Rust 核心提供明确的数据模型、状态机和错误边界，适合做长期可演进的系统骨架。
- 模块化单体有利于以统一事务和一致状态推进首版实现，减少分布式故障面。
- Tauri + Web UI 能兼顾桌面集成能力与高迭代效率，适合快速形成可展示的 AIOS 界面。

### 负面后果

- 该路线不是“真正意义上的新操作系统”，在叙事上需要明确是 AI 时代的宿主级操作环境。
- 仍然受制于宿主 OS 的安全模型、文件系统语义和窗口能力。
- 模块化单体后续若拆分不当，可能形成核心耦合，需要提前定义稳定的内部边界。

## 可逆性

该决策部分可逆。

- 可逆部分：Tauri 外壳可以替换，Web UI 技术栈可以演进，部分模块未来可以拆成独立进程或服务。
- 不可轻易逆转部分：把 AIOS 定位为“运行于宿主之上的可信 Agent 环境”这一产品边界；以及“先单体后拆分”的总体工程策略。

换言之，未来可以调整承载技术，但不应在 MVP 阶段反复摇摆产品层级。

## 验证门槛

该决策成立，必须通过以下门槛验证：

1. 单机闭环：用户能够安装 Agent、发起 Mission、执行 Run、生成 Artifact，并在一次桌面会话中完成闭环。
2. 系统一致性：权限授予、任务状态、产物沉淀和审计记录在单一环境内保持一致，不依赖外部分布式协调。
3. UI 可信度：AIOS 必须拥有独立、可识别、可持续演化的系统界面，而不是零散拼装的网页工作台。
4. 故障恢复：宿主进程异常重启后，Mission / Run / Receipt 状态能够恢复，不出现不受控的重复副作用。
5. 可演进性：当引入第二个 Agent 类别、第二类受保护资源和第二个高风险副作用时，架构无需推倒重来。
