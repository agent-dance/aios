# ADR 0003：Capability Broker 是唯一系统能力入口

- 状态：Accepted
- 日期：2026-07-25

## 背景

AIOS 若要成立，真正必须被“系统化”的不是聊天面板，而是副作用治理：

- 谁在请求能力。
- 这个请求属于哪个 Agent、哪个版本、哪个 Mission、哪个 Run。
- 请求操作的是哪类资源。
- 这个动作是否需要用户确认。
- 若中途崩溃，如何避免重复执行。
- 事后如何证明“发生过什么、为何被允许、结果是什么”。

如果文件、网络、数据库、通知、支付、日历或宿主 API 入口分散在不同模块、不同协议或不同 UI 组件里，最终一定无法回答这些问题。那样的系统既不能安全扩展，也不能可靠审计。

## 决策

AIOS 采用单一 Capability Broker 作为唯一系统能力入口，并围绕它建立授权、确认与审计闭环：

1. 所有会产生外部可观察副作用或访问受保护资源的操作，都必须通过 Capability Broker。
2. Broker 依据 Grant 做权限判断，Grant 与 Agent 身份、版本、空间、任务、运行、资源范围、动作、时效与约束绑定。
3. 所有需要用户知情同意的高风险动作，都必须经过 transaction-bound trusted UI 确认，而不是由 Agent 自绘确认界面代替。
4. Broker 对执行结果产出 Receipt，用于审计、重放保护、恢复与争议排查。
5. 委托只能衰减权限，不能放大权限。
6. 任何协议桥、运行时插件、前端组件或远程 Agent 都不得绕过 Broker 直连宿主能力。

## 设计原则

- 授权检查和副作用执行必须在同一可信边界内闭合。
- “是否允许”与“如何执行”不能分散在不同模块中。
- 高风险确认界面必须由系统绘制，且与待执行事务绑定。
- 所有关键动作都应可追踪、可恢复、可解释。

## 备选方案

### 方案 A：按资源类型分散授权

文件模块管文件权限，网络模块管网络权限，通知模块管通知权限。

### 方案 B：让 Agent 自带确认 UI

由 Agent 通过 A2UI 呈现“请确认”界面，用户点同意后再执行。

### 方案 C：只做日志，不做 Receipt / 事务约束

认为审计日志足够，执行成功或失败由外围系统自行记录。

### 方案 D：只在安装时授权一次，运行中默认放行

把权限集中在安装过程授予，运行时少做或不做细粒度检查。

## 为何排除

### 排除方案 A 的原因

- 授权逻辑碎片化后，无法形成统一的委托、撤销、重放保护和审计链路。
- 不同资源模块会自然长出不一致的权限语义，用户体验和安全结论都不可预测。
- 一旦出现跨资源事务，分散入口几乎无法给出系统级一致性保证。

### 排除方案 B 的原因

- Agent 自绘确认界面无法证明展示内容与真实执行动作完全一致。
- 它会引入典型的混淆与冒充风险：看起来像系统授权，其实只是 Agent 的一层 UI。
- 若确认不是 transaction-bound，就无法保证用户确认的对象与最终执行对象一致。

### 排除方案 C 的原因

- 仅有日志，无法形成强约束的“已批准并已执行”证据。
- 崩溃恢复和幂等保护需要可机器消费的执行凭证，而不仅是人类可读日志。
- 缺失 Receipt 后，后续无法稳定支持撤销、追责、冲突诊断和多步事务分析。

### 排除方案 D 的原因

- 安装时授予的是潜在能力，不等于每次运行都应无条件放行。
- Mission、Run、资源对象和上下文约束在运行时才真正确定。
- 若不做运行时检查，AIOS 会退化成传统粗粒度权限模型，失去“可解释自动化”的核心价值。

## 后果

### 正面后果

- 权限判断、副作用执行、可信确认与审计记录进入统一可信路径。
- 可以用相同机制覆盖本地 Agent、远程协作、MCP 工具桥接和宿主资源访问。
- 事务级 Receipt 为幂等、防重放、恢复和对账提供系统基础。
- 用户可以把“系统确认框”视为 AIOS 的安全承诺，而不是普通 UI 装饰。

### 负面后果

- Broker 会成为核心复杂度集中点，需要很高的工程质量与测试强度。
- 所有能力接入都要经过统一入口，前期会显得比“直接调用”更慢、更繁琐。
- 若 Broker 抽象做得过粗，会压制创新；做得过细，又会放大实现成本。

## 可逆性

该决策几乎不可逆。

可以替换 Broker 的内部实现、存储方式、策略引擎或资源适配器，但不能放弃“唯一系统能力入口”这一原则。只要允许旁路存在，所有授权、确认和审计结论都会失去完整性。

## 验证门槛

该决策成立，至少必须满足以下门槛：

1. 无旁路：代码与运行链路上不存在绕过 Broker 直接访问受保护资源的路径。
2. 授权绑定：Grant 至少与 Agent 身份、版本、Mission / Run 上下文、资源范围、动作类型和时效约束关联。
3. 确认可信：高风险操作的确认界面由系统绘制，并与待执行事务摘要绑定，确认后不得被 Agent 篡改。
4. 凭证闭环：每次关键副作用执行后都生成可查询的 Receipt，能够用于恢复、审计和重放保护。
5. 委托衰减：子委托无法获得超出父上下文的资源范围或动作权限。
6. 崩溃恢复：在确认已完成、执行未完成或执行结果回写中断等情况下，不会产生无法解释的重复副作用。
