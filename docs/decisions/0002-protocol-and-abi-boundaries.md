# ADR 0002：协议边界与 ABI 边界分离

- 状态：Accepted
- 日期：2026-07-25

## 背景

AIOS 的核心创新之一，是让 Agent 不再只是调用若干工具，而是像“可安装能力单元”一样参与系统。这个目标会天然引入多种协议：

- A2UI：用于 Agent 驱动界面呈现与交互描述。
- MCP：用于工具、资源与提示等能力暴露。
- A2A：用于 Agent 之间或本地 / 远程 Agent 之间的协作通信。
- OS 级能力入口：用于文件、网络、密钥、通知、日历、支付、外部副作用等系统能力访问。

如果不提前切开边界，系统会迅速退化为“谁能通就让谁通”的耦合体：UI 协议偷偷拿权限，工具协议顺手做系统调用，远程 Agent 绕过本地授权直接触发副作用。这样不仅不可验证，也不可能形成稳定的第三方生态。

## 决策

AIOS 采用“协议边界与 ABI 边界分离”的原则：

1. A2UI 只负责 UI 描述与交互承载，不直接代表系统能力。
2. AIOS 内部定义稳定的 UI Profile / Surface 模型，A2UI 通过 adapter 映射到该内部模型，而不是直接成为内核级 UI 真相源。
3. MCP 负责能力描述与调用契约，但不等同于系统权限本身。
4. A2A 负责 Agent 间协作与委托，但不天然获得宿主资源访问权。
5. 真正代表“操作系统能力入口”的只有 AIOS 的 Capability ABI；所有外部协议都只能通过该 ABI 获得受控能力。

## 设计原则

- 交互协议、协作协议、工具协议与系统能力 ABI 必须正交。
- 外部标准可以快速演进，但 AIOS 内部稳定模型必须可控。
- 引入标准是为了复用生态，不是把系统边界外包给标准本身。
- 所有协议接入都要经过归一化、校验、政策检查和审计记录。

## 备选方案

### 方案 A：直接把 A2UI 当作系统 UI 真相源

把 Agent 发来的 UI 描述直接渲染为系统界面，不建立内部 UI Profile。

### 方案 B：让 MCP 直接承担权限与能力入口

认为工具能调用什么，就等于 Agent 能做什么。

### 方案 C：让 A2A 远程 Agent 自带能力语义

把远程 Agent 返回的动作视为可信命令，再由本地系统执行。

### 方案 D：统一成一个“大一统协议”

尝试用单一协议同时覆盖 UI、能力、协作、权限和审计。

## 为何排除

### 排除方案 A 的原因

- UI 协议天然变化快，直接作为系统内部真相源会把产品稳定性绑死在外部演进节奏上。
- 缺失内部归一化层后，无法建立 AIOS 自己的组件规范、可信确认边界和兼容策略。
- 未来若切换 UI 协议版本或支持第二类描述协议，迁移成本会变成系统级灾难。

### 排除方案 B 的原因

- 工具契约解决的是“怎么调用”，不是“是否被允许调用”。
- 把权限语义塞进工具协议，会让授权、审计、撤销、委托衰减全部变形。
- 不同工具提供方对权限粒度的表达并不统一，难以形成系统级一致体验。

### 排除方案 C 的原因

- 远程 Agent 的意图、上下文和授权状态无法天然与本地用户会话等价。
- 若远程协作可直接触发本地副作用，就会在身份、同意、审计链上出现断裂。
- “委托”与“执行”必须是两步，不能合并为远程指令直通。

### 排除方案 D 的原因

- 会把系统关键概念混成一个难以演化的抽象泥团。
- 单协议过大后，版本演进、测试矩阵和兼容策略都会失控。
- AIOS 需要的是清晰边界和组合关系，而不是看似统一、实则难以收敛的总线。

## 后果

### 正面后果

- UI、工具、协作和系统能力各自独立演进，降低耦合。
- 可以复用现有生态标准，同时保住 AIOS 自己的内核级判断权。
- 对第三方 Agent 而言，接入边界更清晰：能画什么界面、能声明什么能力、能委托什么任务、能真正触发什么副作用，分别受不同约束。
- 适合做协议适配、版本冻结和兼容策略，便于建立长期平台稳定性。

### 负面后果

- 需要维护 adapter、归一化模型和协议桥接逻辑，前期实现成本更高。
- 开发者会觉得“为什么不能直接通”，需要文档和 SDK 帮助降低理解门槛。
- 系统内部会多出一层抽象，需要工程上保持模型精简，否则容易过度设计。

## 可逆性

该决策低可逆，但局部实现可替换。

- 可替换部分：具体的 adapter 实现、内部 UI Profile 字段设计、协议桥接组件的工程组织。
- 不建议逆转部分：协议边界与 Capability ABI 分离这一原则本身。一旦回退到协议互相越权，平台可信性会直接崩塌。

## 验证门槛

该决策成立，至少要满足以下验证门槛：

1. UI 隔离：Agent 能通过 A2UI 驱动 Surface，但不能仅凭 UI 描述直接触发受保护副作用。
2. 协议正交：同一个 Agent 既可拥有 A2UI 界面，也可声明 MCP 工具与 A2A 协作，但三者的权限判定独立成立。
3. 适配稳定：A2UI 输入经过 adapter 后，内部 Surface 模型可用于渲染、审计、恢复与可信确认协同。
4. 授权闭环：无论能力来自 MCP、本地模块还是远程委托，最终都必须收敛到同一个 Capability ABI 检查路径。
5. 版本演进：当外部协议版本升级或引入第二类 UI / 协作协议时，不需要推翻内部核心模型。
